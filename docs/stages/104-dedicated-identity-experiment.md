## Setup and enrollment

Started installed Tailscale 1.102.3 as an unprivileged second `tailscaled` process with userspace networking, a fresh persistent state file, its own state directory and its own Unix socket. The directory is mode 0700 beneath ignored `artifacts/dedicated-identity-test/`; regular evidence/state files are mode 0600. Existing host state or credentials were not copied.

The experiment uses `TS_DISABLE_PORTMAPPER=true`, automatic UDP port selection and disabled daemon log uploads. Every mutating experiment CLI command includes its explicit socket; the main default socket was used only for read-only comparisons. Experiment-only `up` sets hostname `storagi-test`, DNS and route acceptance disabled, netfilter off and SSH disabled. Read-back preferences confirmed those settings, with no advertised routes or exit node. Userspace operation reports `TUN: false`.

Initial enrollment was pending: `up --timeout=10s` exited 1 with `NeedsLogin` and an owner enrollment URL. The URL remained in ignored private artifacts and private coordinator communication. The coordinator's collaborative browser could not initialize because of the host's browser-sandbox restriction; no host security setting was changed. The owner subsequently confirmed connection, and explicit-socket status verified `Running` with a distinct node ID and DNS name. Browser credentials were not reused autonomously.

## What passed

1. **Separate configuration:** fresh experiment `serve status --json` was `{}`. Native `text:` handlers worked, so no HTTP server, temporary app or directory listing was needed. Experiment HTTPS443 used marker `storagi-isolated-marker-A`; the main daemon already retained its own HTTPS443 mapping. Funnel was enabled only on the experiment socket, without a new tailnet policy prompt.
2. **Actual HTTPS and configuration changes:** after certificate issuance, private tailnet HTTPS returned 200, normal TLS certificate verification succeeded, and the body matched the native text marker. Experiment-only markers A → B → A were each observed over HTTPS. After initial Serve, Funnel enablement and each handler change, the main Serve JSON remained structurally equal to the original complete baseline, including existing mappings and public flags.
3. **Public relay forwarding:** normal public DNS for the new hostname had no A record. A globally routable Funnel relay address was instead discovered through the original host's public DNS. Pinning the new hostname to that relay with curl `--resolve`, retaining correct TLS SNI and certificate verification, returned 200 with exact marker A. The coordinator independently repeated this public relay test successfully after the experiment restart. This demonstrates public forwarding; it does not demonstrate ordinary public DNS resolution or a separate off-tailnet device test. The source host remained Tailscale-connected.
4. **Restart persistence:** verified the owned daemon PID's complete command arguments before sending SIGTERM to that process only. Restarted the same binary with the same state, socket, userspace options and environment. Node ID, DNS name and complete Serve configuration persisted, including the experimental Funnel flag. Verified HTTPS200 and marker A after restart. Updated private PID metadata. The main daemon was never restarted.
5. **Production invariants:** the original Storagi HTTPS dashboard remained 200 and anonymous `/api/session` remained 401 with verified TLS. Main Serve configuration and resolver-file hash matched baseline after restart. No file contents were fetched. The coordinator independently verified the original public relay/dashboard and anonymous-denial checks.

The coordinator observed one dynamically discovered host route for the new Tailscale peer, with no removed routes; the route table is therefore not claimed byte-unchanged after enrollment. No route was manually added, removed or restored by this experiment.

## Failures and remaining gap

- The first HTTPS fetch timed out during initial certificate provisioning. Targeted daemon evidence showed transient control-plane EOF failures, followed by successful certificate issuance and successful retried HTTPS. A separate coordinator public relay attempt overlapped the experiment restart and timed out during TLS handshake; its bounded retry passed. These failures are retained rather than represented as uninterrupted availability.
- Google and Cloudflare public DNS returned NOERROR with no A/AAAA answer for the new hostname. A direct recursion-disabled query to an authoritative server also returned NOERROR, authoritative (`aa`), zero answers and an SOA authority record. This is an authoritative missing record at the time checked, not merely a recursive negative-cache effect. The authoritative negative TTL was 300 seconds. A final bounded set of eight queries compared both names and both A/AAAA types across two authoritative servers (UDP to one, TCP to the other). Every response was authoritative NOERROR: the original hostname had two A and two AAAA answers on each server, while the new hostname had neither address type on either server. Thus no IPv6-only public path was observed. Initial Funnel enablement was 2026-10-24 00:01:34 +08:00; the eight-query comparison finished at 00:07:27, approximately six minutes later. This observation does not establish a permanent condition or its cause. One final unchanged-configuration check at approximately 00:12:30 +08:00 (10.94 minutes after first enablement) still found no A or AAAA answers from either the authoritative server or Google recursive DNS. The bounded provisioning window therefore ended without normal public DNS success; there is no indefinite watcher or repeated reconfiguration. Exact upstream cause remains unproven. No normal browser-only public URL success is claimed; later provisioning must be checked before any migration decision.
- Unprivileged userspace startup logged inability to increase UDP buffers, unavailable TUN interface statistics and unavailable TPM access. The process nevertheless reached Running and passed the recorded endpoint/restart tests. This is not a production hardening or throughput result.
- Separate configuration prevents routine default-socket commands from overwriting this node's Serve settings. Both experiment and host sockets remain controllable by the same owner UID, so this is not a security boundary against a process deliberately targeting either socket. A permanent deployment would need appropriately restricted daemon control/state and supervision.
- No speed improvement, Google login at the new origin, production data access, OAuth callback registration, boot startup or permanent installation was tested. Existing production origin, Google owner checks and OAuth client were unchanged.
