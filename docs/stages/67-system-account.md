## Decisions

- **No dual mode** (owner). `deploy/storagi-user.service` is deleted; `docs/user-service.md` is a short superseded pointer; the new guide is [docs/system-service.md](../system-service.md).
- **The copy reads with the caller's uid.** A root `cp -R` of a caller-owned tree follows swapped intermediate directories (path-based traversal), so a caller could make root copy files from the owner's home or `/etc` into a release. Unhashed paths such as `docs/` would then pass verification and become world-readable. Instead `setpriv --reuid/--regid/--clear-groups` runs `tar -c` as the caller, and root extracts the stream with `tar --no-same-owner --no-same-permissions` in a transient unit with no capabilities, writing only the new release (`ProtectSystem=strict`, `ReadWritePaths=<release>`, `ProtectHome`, `PrivateDevices`, `NoNewPrivileges`, `RuntimeMaxSec=300`). The helper then clears write, setuid, setgid and sticky bits and requires only owner-owned regular files, directories and symlinks, every symlink resolving inside the release.
- **Release code runs only as `storagi`.** `verify-release.sh` from the new release and both config checks run through `systemd-run --uid=storagi` with `RuntimeMaxSec=60`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp` and `NoNewPrivileges`. The helper has no trusted copy of `verify-release.sh`: the release's own check against its own manifest cannot bind a caller who chooses the code anyway. Its value is integrity, and it now runs on the root-owned copy that nobody else can change before the start.
- **Root does not trust what release code prints.** The config check is release code, and root uses its output for the backup source, `ss` and `curl`. The helper requires a numeric port, a plain `host[:port]` and exactly `/var/lib/storagi/storagi.sqlite`, and the backup copies only regular files, not symlinks.
- **The installed unit is never touched by a deploy.** No unit install, `daemon-reload` or unit backup; rollback restores only `current`. The old rollback test "a failed unit restore with a healthy service" no longer applies and is replaced by a failed `current` restore.
- **Environment.** `#!/bin/bash -p` (no `BASH_ENV`, `SHELLOPTS` or exported functions), every exported variable unset after reading `SUDO_UID`/`SUDO_GID`, then fixed `PATH`, `IFS`, `LC_ALL=C`, `umask 022` and `cd /`. `curl -q --noproxy '*'` ignores any `.curlrc` and proxy. `SHELLOPTS` cannot be unset (readonly); with `-p` it holds bash's own options, not the caller's.
- **Test seam.** The installed helper has only literal path constants; the tests run a copy with exactly those seven lines rewritten (asserted). EUID-conditional overrides were rejected: override code would sit in the root binary, one edit away from a caller-controlled seam.
- **Lock** on the `/opt/storagi` directory fd (`flock`), no lock file.
- **Unit sandbox** as the owner listed; not `MemoryDenyWriteExecute`. Other directives that `systemd-analyze security` still flags (`SystemCallArchitectures`, `RemoveIPC`, `PrivateUsers`, `IPAddressDeny`) are outside the owner's list and were not added.

## Findings and limitations

- Process slip during implementation, no effect: a mis-terminated heredoc ran the tail of a draft as shell commands, including `sudo /usr/local/sbin/storagi-promote ""`. sudo refused it ("a terminal is required to authenticate"), and that path did not exist. A later `sudo -n true` probe was also refused ("interactive authentication is required"). Nothing was installed or changed: `/usr/local/sbin` and `/opt` were checked afterwards, and the live service, runtime and configuration were not touched.
- Limits recorded in the guide: the deploy account chooses the code `storagi` runs; the copy is not size-bounded; a caller can stop sudo and leave the service down until resumed. Release integrity rules (manifest, hash, links in hashed paths) are enforced by the release's own `verify-release.sh`, as at `ExecStartPre`; they guard against accidents, not a caller who chooses the code.
