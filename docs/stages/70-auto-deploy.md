## Decisions

- **Self-updating poller.** `scripts/storagi-autodeploy` runs from the account's clone. Each tick it takes a lock, mirrors origin (`fetch --force --prune --prune-tags --tags`, so moved and deleted tags are followed), resets the clone to `origin/main` and re-executes itself from the clone with the lock fd inherited, so the poller and `deploy.sh` that run are reviewed `main`. Its body is one `main` function parsed before it runs.
- **Which tag.** The highest strict `vX.Y.Z` (no leading zeros or suffix) whose commit is on `origin/main`, deployed only if newer than the live `TAG=` (read with `sed`, never sourced) and than every tag in the state file. Only the highest is considered: if it failed, an older not-yet-tried tag is not deployed instead (that would ship code older than the owner's latest intent).
- **State as a high-water mark.** `autodeploy.state` lists every tag tried (`exit-N`, `ci-failed`) or first seen live (`live`). Using the maximum rather than a failed list also covers manual rollback: a tag the owner rolled back from is not redeployed. Busy and pending ticks record nothing.
- **CI.** Anonymous `check-runs?check_name=check` for the tag commit; only runs from the `github-actions` app count (another installed app cannot report a fake `check`). No run or not completed: pending; all `success`: deploy; otherwise `ci-failed`, alerted once. HTTP 403/429, other statuses, no network and unparsable JSON: next tick, nothing recorded. Checked against the real API for `v1.0.1` (`0de583f`): one Actions `check` run, `success`.
- **Exit 75 (EX_TEMPFAIL).** `storagi-promote`: lock held and both open-connection checks (an `ss` failure still counts as busy), with the build-phase cleanup preserving 75. `deploy.sh`: fetch failure, `ls-remote` failure and HEAD not `origin/main` (the clone was reset seconds earlier, so this is `main` moving on). Without these, a network blip or a merge during a tick would permanently mark a good tag failed. `deploy.sh` also gained `trap 'exit 1' ERR`: before, a build step exiting 2 or 3 (for example `tar`) made `deploy.sh` exit 2 or 3, which reads as "rolled back" or "MANUAL RECOVERY REQUIRED". Manual use is unchanged apart from these codes.
- **sudoers.** sudo on this host is sudo-rs 0.2.13, which forbids wildcards inside arguments (`visudo -c` rejects `storagi-promote /var/lib/storagi-deploy/.cache/storagi/staging/*`), so `deploy/storagi-deploy.sudoers` names the command only; the helper validates its single argument (canonical path, owned by the caller, release-name shape). sudo-rs always resets the environment, sets `HOME` from the target and `SUDO_UID`/`SUDO_GID` from the caller, so the helper's caller gates (nonzero `SUDO_UID`, staging dir owned by it) accept `storagi-deploy`, and `deploy.sh`'s `$HOME/.cache/storagi/staging` resolves under `/var/lib/storagi-deploy` with no symlink. No helper or `deploy.sh` gate needed changing for the account.
- **Webhook.** `LoadCredential=` from `/etc/credstore/storagi-discord-webhook` (root 600; `/etc/credstore` already exists on this host). Bash reads the file, checks the Discord URL shape, and passes it to curl as `-K /dev/fd/N` from a `printf` builtin, so it is not in any argv, log or the state file. A failed post is logged and ignored.
- **Unit sandbox.** sudo and the helper run inside the unit's namespace, so every setting binds root too. systemd 259's `systemd.exec(5)` no longer implies `NoNewPrivileges` for seccomp settings in system units, but those filters would still apply to sudo-rs's PAM stack, `setpriv` and `ss`, none of which can be run as root here; so `SystemCallFilter` and `RestrictAddressFamilies` stay off, as do `NoNewPrivileges`, `CapabilityBoundingSet`, `PrivateDevices`, `ProtectClock` and `RestrictSUIDSGID`. Kept: `ProtectSystem=strict` with `ReadWritePaths` for the home and the helper's two trees (whose permissions keep the account out), `ProtectHome`, `PrivateTmp`, `ProtectProc=invisible` (root is unaffected, which the helper's `/proc/<pid>/cwd` check needs), kernel/cgroup/hostname protections, `RestrictNamespaces`, `RestrictRealtime`, `LockPersonality`, `SystemCallArchitectures=native`, `UMask=0077`. Per-setting reasons are in the guide. `TimeoutStartSec=30min`; `TimeoutStopSec=5min` leaves the helper's rollback (up to about 150 s) time before SIGKILL.

## Findings and limitations

- No alert while a tag waits (CI pending, busy, offline); a long-lived busy state is visible only in the journal. A stop mid-deploy (shutdown) may end the run before it records or alerts; the helper still rolls back and the next tick retries.
- Build code (`npm ci` install scripts from the reviewed lockfile) runs as `storagi-deploy` and can read the webhook credential during the run, and through the helper could choose the code `storagi` runs, as recorded since stage67.
- The human pause between a tag push and cutover is gone: a stolen owner GitHub session could ship code within 15 minutes, still only as `storagi` in its sandbox.
