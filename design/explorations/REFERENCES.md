## Features the owner asked for, and what the real app needs

**Live upload speed and finish time.** tus-js-client already reports `onProgress(sent, total)`. Speed is an exponential moving average over one-second windows; ETA is the bytes left divided by that speed, shown after two seconds of samples so it does not swing wildly; the finish time is now plus the ETA. For the queue, ETA counts every queued byte at the current speed. All of this is client-only.

**Live download speed.** Today a download is a plain link, so the browser owns it and the page cannot see its progress. Two routes:
1. Keep the plain link (works for multi-GB files on every browser, including Android) and show no in-page progress — the browser's own download UI shows speed.
2. Download through `fetch()` and read the stream to count bytes. Writing a multi-GB file then needs the File System Access API (`showSaveFilePicker`, Chromium desktop only) or a service-worker stream; Firefox and Android Chrome would fall back to route 1. Recommendation: route 2 where `showSaveFilePicker` exists, route 1 elsewhere, and say which is in use.

**Auto-refresh.** Poll `GET /api/files` every 60 s while the tab is visible, at once when the tab becomes visible again after more than 10 s, and after each finished upload; never while hidden. Keep the old list on screen during a refresh and show "Updated 12s ago · next in 48s" with a manual refresh. A later step could replace polling with server-sent events from the service.

**Koi motion.** The koi swim by default even when the OS asks for reduced motion (owner's choice). A per-browser setting, "Follow system setting", restores the reduced-motion behaviour; it applies live so uploads are not interrupted.

**Favicon.** The owner's grayscale kohaku curl is in `shared/brand/` and `web/public/favicon.svg`. The `.ico`, PNG and touch icons need `server/src/static.ts` to allow them before production serves them.
